# Development, staging and production setup

## Vercel web deployment

Set the Vercel project's **Root Directory** to the repository root (`./`), not `apps/web`. The root `vercel.json` pins the Vite framework, `npm ci`, `npm run build:web`, and `apps/web/dist`. This installs the npm workspaces and builds `packages/shared` before TypeScript compiles the web app. The root Node engine selects Node 22.x, matching GitHub Actions; select 22.x in Vercel's Node.js Version setting as well. The same Vercel project also serves the Express API through `api/index.ts` under `/api/v1/*`.

Set these build-time environment variable names in Vercel for the appropriate Preview and Production environments: `VITE_API_BASE_URL`, `VITE_SUPABASE_URL`, and `VITE_SUPABASE_PUBLISHABLE_KEY`. `VITE_API_BASE_URL` must be the publicly reachable Express API origin ending in `/api/v1`; a `localhost` value only works on the developer's machine. The Supabase values are public Auth configuration. Never add `DATABASE_URL`, database passwords, CA files, or service-role keys to a `VITE_` variable. Preview and Production have separate environment settings, and a change requires a new deployment. A Ready build does not prove the API function starts: check `/api/v1/health` and `/api/v1/health/ready` on the exact deployment URL.

| Variable | Required environment | Visibility | Consumer / fallback |
| --- | --- | --- | --- |
| `DATABASE_URL` | Vercel Preview/Production API, Render API | Secret | PostgreSQL pool; no production fallback |
| `DATABASE_SSL` | API | Server only | Verified TLS defaults on in production; `false` is rejected |
| `DATABASE_SSL_CA` | API when a private CA is needed | Server only | Inline PEM certificate or certificate chain; escaped `\n` is normalized |
| `DATABASE_SSL_CA_PATH` | API when a private CA is needed | Server only | Path to a readable CA file included in the server deployment; takes precedence over `DATABASE_SSL_CA` |
| `SUPABASE_URL` | API and corresponding public client configuration | Public URL | Auth project origin; no production API fallback |
| `SUPABASE_PUBLISHABLE_KEY` | API | Publishable | Auth token verification; no production API fallback |
| `CORS_ORIGIN` | Vercel Preview/Production API, Render API | Server only | Comma-separated exact web origins; no production fallback |
| `SUPABASE_SECRET_KEY` | API only when Admin invitations are enabled | Secret | Invitation service; unrelated Auth routes do not require it |
| `VOLUNTEER_INVITE_REDIRECT_URL` | API when invitations are enabled | Server only | Exact HTTPS `/accept-invite` URL; optional otherwise |
| `PUBLIC_VOLUNTEER_REGISTRATION_ENABLED` | API only after separate public-registration approval | Server only | Exactly `true` enables unauthenticated email-sending registration; absent or any other value keeps it disabled |
| `VITE_API_BASE_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` | Web build | Browser public | Web API/Auth clients; build-time values |
| `EXPO_PUBLIC_API_BASE_URL`, `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Mobile build | App public | Mobile API/Auth clients; build-time values |
| `EXPO_PUBLIC_WEB_BASE_URL` | Mobile build for Volunteer recovery | App public | Exact HTTPS web origin; opens the public `/forgot-password` page |

Missing required API settings are logged as `ServerConfigurationError` with variable names only. Liveness remains available; readiness and protected routes return `503 SERVER_CONFIGURATION_ERROR`. Never place `SUPABASE_SECRET_KEY` in a browser or mobile variable.

From a clean checkout, reproduce the deployment build with `npm ci` followed by `npm run build:web` at the repository root. Confirm `npm ls @aaharaconnect/shared --workspace apps/web --depth=0` shows the local workspace link. After a deployment, verify the actual URL and Auth settings in the Vercel dashboard without copying their values into Git or logs.

## Required services and secrets

Use one Supabase project per environment (development, staging, production) when possible, each with its own PostgreSQL database and Supabase Auth configuration. Enable supported email sign-in and email confirmation. Set the project's URL and publishable key on the Express server; these identify the Auth project but are not an administrator secret. The database connection string is server-only. Never put `DATABASE_URL`, database passwords or Supabase secret/service-role keys in `VITE_` or `EXPO_PUBLIC_` variables. The frontends may later receive only the project URL and publishable key for authentication; their application-data URL remains the Express `/api/v1` URL.

Set `PORT`, `NODE_ENV`, `CORS_ORIGIN`, `DATABASE_URL`, `DATABASE_SSL`, `DATABASE_SSL_CA` or `DATABASE_SSL_CA_PATH`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `LOCATION_RETENTION_DAYS` on the server. The development session-pooler connection was verified with `DATABASE_SSL=true`, the project's downloaded CA certificate, and `rejectUnauthorized=true`. Inline PEM is validated and supports escaped newlines; when both CA settings are present, the file path takes precedence. Keep CA material server-only and never disable verification to make a connection pass. `SUPABASE_URL` must be the project API origin (`https://PROJECT_REF.supabase.co`), not the dashboard page. Set `VITE_API_BASE_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` for web and the corresponding `EXPO_PUBLIC_*` values for mobile. Only the project API URL and publishable key may be client-visible. Copy workspace `.env.example` files for local development; deploy secrets through the hosting platform, never Git. Use the Supabase Connect panel's server connection or session-pooler URI appropriate for a persistent Node process and keep the pool small. Test staging separately before production.
When using the `pg` client's `DATABASE_SSL` options, do not add conflicting `sslmode` parameters to the URL; provide the trusted CA with `DATABASE_SSL_CA` or `DATABASE_SSL_CA_PATH` if the host certificate needs one.

Admin Volunteer invitations require `SUPABASE_SECRET_KEY` **only on the Express server**. Keep it out of Vite/Expo configuration and Git. For the complete invite flow, set `VOLUNTEER_INVITE_REDIRECT_URL` to the public web acceptance URL: `http://localhost:5173/accept-invite` locally or `https://<web-domain>/accept-invite` in production. The server accepts local HTTP only for loopback hosts outside production. Add the exact URL for each environment to Supabase Auth **Redirect URLs**; set the Supabase **Site URL** to the correct web origin. The redirect setting is needed for this flow because the web origin alone opens the landing page. The default Invite User email template must retain its confirmation link. The public `/accept-invite` page restores the Supabase invite session, lets the Volunteer choose a password through Supabase Auth, signs out that temporary web session, and directs the Volunteer to sign in on mobile. The Admin never receives the password. A future custom invite template may link to `https://<web-domain>/accept-invite?token_hash={{ .TokenHash }}&type=invite`; this is optional and the default confirmation link remains supported. Redeploy the server after setting its environment variables.

For the Admin-invited pilot, leave `PUBLIC_VOLUNTEER_REGISTRATION_ENABLED` absent or `false`. The public `POST /volunteers/register` route then returns `403 REGISTRATION_DISABLED` before validation, database access, or Supabase invitation; the authenticated Admin invitation route remains available. Enabling public registration requires separate approval and server-side email-abuse controls such as rate limiting. Do not rely on hiding a mobile button or on CORS to protect an unauthenticated API route. Never put the Supabase secret key in a client build.

Supabase hosted development email delivery has restrictions: its default sender may reject addresses outside the project team and has a low shared email limit. `INVITE_EMAIL_NOT_AUTHORIZED` identifies the address restriction; `INVITE_RATE_LIMITED` identifies the send limit. For production invitations, configure and verify suitable SMTP/email delivery in the Supabase dashboard, including sender settings and delivery monitoring. The code does not configure a mail service or guarantee delivery. Test a disposable invitation end to end before a live pilot. The web deployment must serve `index.html` at `/accept-invite`; the repository's Vercel configuration includes this route rewrite. Other hosts need an equivalent SPA fallback for that path.

If an invitation returns `429 INVITE_RATE_LIMITED`, wait for the provider's limit window before retrying; do not send repeated requests. In development, inspect the safe `SupabaseAuthInvite` log entry for provider HTTP status and code. Production requires a verified SMTP provider and matching Auth Site URL and Redirect URLs. If provisioning returns `INVITE_RECOVERY_REQUIRED`, the invitation may exist while application records do not. Inspect Supabase Auth and the canonical `app_users`/`people`/`volunteers` records before retrying; never delete or repurpose an existing account automatically.

Volunteer password recovery uses only the public web Supabase Auth client. The mobile `EXPO_PUBLIC_WEB_BASE_URL` must be the exact HTTPS origin of the web deployment; the browser requests recovery with a fixed redirect to that origin's `/reset-password` route. Add that exact callback URL to the corresponding Supabase Auth Redirect URLs and verify the Recovery email template retains a working recovery link. The current callback accepts Supabase's implicit recovery redirect or an explicitly configured `token_hash` link with `type=recovery`; it rejects PKCE `code` callbacks until that flow is separately implemented and tested. The Vercel SPA configuration serves both `/forgot-password` and `/reset-password`. Recovery depends on working Auth email delivery and provider rate limits. It never changes application roles, Volunteer approval, or operational status. A successful Auth password change is not a promise that existing access tokens have been immediately revoked. Test this flow only with disposable staging accounts before enabling it for a real pilot.

## Migration procedure

1. Use a separate database and backup for each environment. Confirm the connection target, schema permissions, and extension `btree_gist` availability.
2. Run `npm ci` from the repository root with Node 22.13 or newer within the 22.x line.
3. Set the **server** `DATABASE_URL` and SSL settings. Inspect the target database's migration ledger and pending SQL before running `npm run migrate:status --workspace server` and, only after review, `npm run migrate:up --workspace server`. The verified Production ledger records seven migrations, `001_core.sql` through `007_vessel_photo.sql`, and does not contain `005_functions.sql`. A different development database historically records `005_functions.sql`, whose original SQL is unavailable. The runner does not require that historical entry when absent; if present, it accepts only the pinned SHA-256 `94bab7ac366215d29fd7346ed61ffb929a9858acb8cf2a6e58f5b8055080e94c` and warns that source comparison is unavailable. It rejects every other missing applied file, changed checksum, or duplicate active migration number. Do not recreate historical SQL or modify the ledger. Volunteer Applications requires pending migration `008_volunteer_applications.sql` before deploying application code that reads its status. An environment that already applied the older `007_volunteer_applications.sql` filename must be reconciled separately; the runner will fail rather than replay it as 008.
4. Apply to development first, then staging after tests, then production during a reviewed release window. Never run two migration jobs at once; the runner also takes a PostgreSQL advisory lock and records checksums.
5. Applied SQL files are immutable. Correct a defect with a new forward migration; restore from a tested backup if necessary. Review data migrations separately from schema-only changes.

The migration runner uses the repository's `server/db/migrations` directory and the connection string of the current environment. It does not create Supabase projects. The `app` schema is private to Express; do not expose it through Supabase's Data API or place DB credentials in clients. Active migration filenames must have unique numeric prefixes. The runner accepts a missing historical `005_functions.sql` source file only when its applied ledger checksum matches the pinned value above; it does not require that ledger entry in databases that never applied it.

## First administrator

After a trusted maintainer signs up with a **confirmed email**, call `GET /api/v1/me` with their Supabase Auth access token so `app.app_users` creates a DONOR row. An integration maintainer then uses a privileged SQL session against the correct environment to promote **that exact verified `auth_user_id`**:

```sql
UPDATE app.app_users SET role = 'ADMIN', updated_at = now()
WHERE auth_user_id = '<verified-auth-user-uuid>' AND role = 'DONOR';
```

Confirm exactly one row changed and record the bootstrap in the release log. After bootstrap, only an ADMIN may grant VOLUNTEER or ADMIN via `PATCH /api/v1/admin/users/:id/role`; that endpoint writes an audit event. Do not add an environment variable that silently grants admin by email.

## Runtime and pilot checks

### Demonstration release gate

1. For an existing database, compare every `app.schema_migrations` filename and checksum with the checkout before executing anything. The verified Production history has seven applied files ending at `007_vessel_photo.sql`; pending `008_volunteer_applications.sql` must be reviewed and staged before Production. If another database records `005_functions.sql`, verify its pinned checksum above; if it records old `007_volunteer_applications.sql`, stop for environment-specific reconciliation. Test a fresh database separately before relying on it for staging.
2. Build and test from the repository root: `npm ci`, `npm run build:shared`, `npm run build:server`, `npm run build:web`, `npm run test:server`, `npm run test:web`, `npm run check:mobile`, and `npm run lint:mobile`.
3. On a persistent Node host, set the server variables above, build with `npm run build:server`, and start with `npm run start --workspace server`. Check the public `/api/v1/health/ready` URL before pointing clients at it. Set `CORS_ORIGIN` to the exact web origin.
4. Deploy the static web app from the repository root using the checked-in `vercel.json`. Set its public API and Supabase Auth variables before building. Add the exact public `/accept-invite` URL to Supabase Auth redirects and verify the Site URL.
5. The existing `apps/mobile/eas.json` preview profile builds an installable Android APK. From `apps/mobile`, after setting a public `EXPO_PUBLIC_API_BASE_URL` and public Supabase Auth settings for the build, run `npx eas-cli@latest build -p android --profile preview`. Download the APK from the completed EAS build page and install it on the test phone. Do not point an APK at `localhost` or a private laptop LAN address.
6. Validate Admin, Volunteer, and Donor flows against the public API before calling the demonstration end to end. Donor mobile live mode now submits, lists, reads, and cancels requests through Express; those flows still require a real DONOR session and database end-to-end test. Live Admin vehicle assignment belongs to Pickup & Logistics, not the browser's local donor trip store.

Build with `npm run build:shared`, `npm run build:server`, `npm run build:web`; run `npm run check:mobile`, `npm run lint:mobile`, `npm run test:web`, and `npm run test:server`. `GET /api/v1/health` is liveness; `/api/v1/health/ready` checks the database. Monitor request IDs, 5xx/409 rates, pool saturation, auth failures and migration version. Run `npm run prune:locations --workspace server` daily once tracking is enabled; location writers must set `expires_at` using `LOCATION_RETENTION_DAYS` and require active pickup plus consent. No continuous background GPS is required.
The database integration tests run only with `TEST_DATABASE_URL` naming a dedicated database ending in `_test` and `ALLOW_TEST_DATABASE_MUTATION=true`; HTTP integration tests also require `DATABASE_URL` to equal `TEST_DATABASE_URL`. CI supplies an ephemeral `aahara_test` database, disables Supabase SSL for that local PostgreSQL service, and applies migrations `001`–`003` before testing. Never point these tests at staging or production. CI fails if the HTTP database tests are accidentally disabled.

Before any real-user pilot, complete and test domain endpoints, frontend auth and mock-to-live mappings, donor safety review, assignment transitions, failure recovery, authorization, explicit tracking consent, data retention, backup restore and staging end-to-end flows. This foundation alone is **not** production ready.

The web Settings page and the mobile login screen's separate shared-API action can authenticate with Supabase when their public settings are configured; mobile keeps sessions in Expo-compatible AsyncStorage. The original sign-in and explicit demo path still use local mock data. The web admin screen requires a server-owned ADMIN role for its Auth connection; a DONOR token cannot become ADMIN through client state. Rotate temporary test passwords after use and remove local `SUPABASE_TEST_EMAIL`/`SUPABASE_TEST_PASSWORD` entries when no longer needed.
