# Canonical data model

The numbered SQL migrations in `server/db/migrations` define the PostgreSQL `app` schema and module extensions. The verified Production ledger records `001_core.sql` through `007_vessel_photo.sql`, including `005_vehicle_assigned_driver.sql`, and does not record `005_functions.sql`. A different development database historically applied `005_functions.sql`; its original SQL is unavailable in this checkout. All primary keys are UUIDs; timestamps are `timestamptz` and sent to clients in UTC ISO 8601 form. Quantity values always carry a unit.

| Owner | Tables | Relationships and invariants |
| --- | --- | --- |
| Central | `app_users`, `user_role_events`, `people`, `schema_migrations` | `app_users.auth_user_id` is the verified Supabase identity. New identities default to DONOR. A person optionally links to one app user and has one unique normalized phone; the same `person_id` may appear in volunteer and driver records. Role changes are audited. |
| Volunteer | `volunteers`, `volunteer_applications`, `volunteer_availability`, `teams`, `team_members` | One volunteer per person. Applications link one-to-one to the canonical `volunteers` row; applicant name, phone, email identity and registration details remain in `people`, `app_users`, and `volunteers`, not duplicated. New self-registration creates an INACTIVE Volunteer and a PENDING application. ADMIN review records `reviewed_by` and `reviewed_at`; approval activates the profile and denial keeps it inactive. Legacy Admin-created Volunteers without application rows retain existing access and operational status. A volunteer belongs to at most one team in the initial release. Service must verify that the leader is a team member and that availability covers the whole reservation window. |
| Food | `donors`, `food_requests`, `food_items` | One donor profile per app user. Request stores preparation time, ready time, pickup deadline, safety declaration and a separate manual `safety_review` initially PENDING. Safety declaration is not safety approval. Food items have positive quantity and explicit unit. |
| Module 5 — Vehicle Details Maintenance | `vehicles`, `drivers`, `vehicle_unavailability`, `vehicle_maintenance_records` | One canonical vehicle row per unique registration and one driver row per person. `kind` is vehicle type; `capacity_kg` is weight capacity. Optional `size_category` and `indicative_max_vessels` are specifications, not pickup reservations. Maintenance history records service date, condition and next due date. The latest record can inform condition; status and unavailability windows govern dispatch. |
| Module 4 — Vehicle Tracking and Management | `vehicle_tracking_consents`, `vehicle_locations` | A location references Module 5's canonical vehicle, Module 3's pickup, reporter and that reporter's recorded consent; expiry is mandatory. No background tracking is required. |
| Pickup | `pickups`, `assignments`, `assignment_members`, `resource_reservations`, `container_plans`, `assignment_status_events`, `pickup_status_events`, `idempotency_keys` | One pickup per food request initially. One active assignment per pickup. Team assignments snapshot explicit participating volunteers. Each person/vehicle reservation references the assignment. Status changes have audit events and versions. |

`resource_reservations.person_id` covers **both volunteer and driver bookings**, so a person serving in both roles cannot occupy overlapping windows. A row represents either one person or one vehicle. GiST exclusion constraints reject overlapping active time ranges for the same person or vehicle; the `[start,end)` boundary allows adjacent bookings. Booking services must still lock and recheck food readiness, volunteer slots, driver licence, vehicle maintenance/capacity and team membership in one transaction. A unique phone and shared person record reduce duplicate identities, but administrators must resolve suspected duplicate people before dispatch; the database cannot infer that two unrelated names are the same human.

Vehicle capacity is kilograms. Meal counts cannot automatically establish kilograms; the Food team must provide a reviewed estimate or the coordinator must record an explicit estimate before vehicle assignment. `container_plans` records type, count and estimated load; reusable container asset tracking is outside the first release. A reporter's consent is a separate server record and must be current; a client boolean is not sufficient. `vehicle_locations.expires_at` enables retention cleanup, configured by `LOCATION_RETENTION_DAYS`; the deployment must schedule `prune:locations`.

Migration `003_vehicle_details.sql` leaves existing vehicles valid while adding optional size and indicative vessel specifications plus maintenance history. Vehicle downtime remains in the existing `vehicle_unavailability` table. Database triggers serialize reservation, downtime and status changes on the canonical vehicle row: an inactive vehicle or overlapping downtime rejects an active vehicle reservation, and active future reservations block conflicting downtime/status changes. Pickup's transaction must still check all dispatch preconditions and release reservations on cancellation, failure or completion. The Module 5 assigned-people view reads Module 3 `assignments` and `assignment_members`; there is no second assignment table or editable roster on `vehicles`.

Only integration maintainers change migrations. Never edit an applied migration; add a new SQL file with a unique numeric prefix. The runner rejects duplicate active prefixes, records SHA-256 checksums, and rejects changed or missing applied files except for the narrowly pinned historical `005_functions.sql` ledger entry. Verify the target ledger before execution. Apply migrations separately to development, staging and production after backup and review. See `DEPLOYMENT.md`.



`008_volunteer_applications.sql` adds a one-to-one application record keyed by the canonical Volunteer ID, constrained status, submission/review metadata and a pending-review index. It enables RLS and revokes direct Supabase API-role access; Express continues to use its server-only PostgreSQL connection. Migrations 009 and 010 add the reviewed cancellation timestamp and food item measurements without rewriting existing rows. New `011_volunteer_registration_rate_limits.sql` adds a server-only HMAC-keyed table for distributed IP/email rate limits; it enables RLS, defines no client policies and revokes Supabase API-role privileges. It does not store raw IP addresses or email addresses. Do not enable public registration until 011 is applied and verified in the target environment. Migration files 001–010 remain immutable; the runner rejects changed checksums or duplicate prefixes. The historical `005_functions.sql` exception is accepted only when its ledger checksum matches `94bab7ac366215d29fd7346ed61ffb929a9858acb8cf2a6e58f5b8055080e94c`; do not reconstruct it or edit migration history.

## Migration 012 — employee drivers and pickup administration

- `drivers.driver_type` is `EMPLOYEE` (NGO staff, created from Assign Driver) or `LEGACY_VOLUNTEER` (every pre-012 row; kept readable for historical assignments, not assignable to new pickups). Added `employee_code` (unique when present), `created_at`, `updated_at` and `created_by`. Type and person are immutable (trigger `drivers_identity_guard`). An `EMPLOYEE` driver's person must have no login and no Volunteer record.
- The fixed link is the existing `vehicles.assigned_driver_id`. The partial unique index `vehicles_one_vehicle_per_driver` plus the single column give one driver ↔ one vehicle. Trigger `vehicles_fixed_driver_guard` forbids changing or clearing an employee driver's link, creating a vehicle that already carries an employee driver, and deleting a linked vehicle. The deferred constraint trigger `employee_driver_requires_vehicle` makes an employee driver without a vehicle impossible at commit. Vehicles are still created with no driver, so there is no circular dependency.
- `pickups.food_request_id` uniqueness is now the partial index `pickups_one_open_pickup_per_food_request` (`status <> 'CANCELLED'`), so an Admin-cancelled pickup no longer blocks rescheduling the same donor request. `pickups.operational_notes` was added. `pickup_schedule_changes` audits every Admin edit (RLS enabled; no client grants).
- The migration stops with an explicit error, rather than unlinking anything, if legacy data links one driver to several vehicles. Rollback statements are in the migration header and are safe only before any employee driver or rescheduled request exists.

## Migration 013 — driver sign-in and acknowledgement

- `app_users.role` adds `DRIVER`. A driver's Auth identity links through the existing `people.app_user_id`, so drivers are never Volunteers.
- `drivers.login_email` stores the invited address in lower case (unique when present).
- `assignments.driver_acceptance` (`NOT_REQUIRED`, `PENDING`, `ACCEPTED`, `DECLINED`) and `driver_responded_at` record the driver's own response, separate from the shared crew status. Existing rows are `NOT_REQUIRED`. Driver responses write `assignment_status_events` rows (same from/to status) and increment `version`.
